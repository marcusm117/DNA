2. Semi-Formalized Structure: For the Semi-Formalized Structure, you must output a json5-style structure (you should interleave comments as chain-of-thought style reasoning in between data) with 3 fields "quantification", "premises" and "conclusions" at the top level.

quantification: A string explaining the quantification of the entire statement, for example, 'for all $n$, $f$, possibly other variables'.

premises: A list of strings of English clauses (directly quantified by the top-level quantifier), or sub-structures representing a statement with nested quantifiers. For example, a premises like "suppose there exists a function $g$ such that g has some property", then you should break it down into a sub-structure.

conclusions: A list of strings of English clauses (directly quantified by the top-level quantifier), or sub-structures representing a statement with nested quantifiers.

{   
   "quantification": quantification string,
    "premises": [
        English clause 1,
        English clause 2,
        {
            "quantification": ...,
            "premises": [
               English clause 1-1,
               English clause 1-2,
               ...
               ],
            "conclusions": [...]
        }
        English clause 3,
        ...
    ],
    "conclusions": [
        English clause 1,
        English clause 2,
        {
            "quantification": ...,
            "premises": [...],
            "conclusions": [...]
        }
        English clause 3,
        ...
    ]
}

Each clause is an English sentence representing a mathematical statement quantified by its upper-level quantifiers. The relationship between premises and conclusions is implication. The relationship between each clause is conjunction. So for clauses quantified by the same top-level universal quantifier, you can easily formalize them into the binder form.

You should try to make each clause and sub-structures as atomic as possible i.e. within a clause or a clause in a sub-structure, there shouldn't be any logical operators. If there has to be some, you should use as few logical operators within a clause as possible, and use multiple clauses instead to express the same meaning.

10. Common Error & Fix **READ CAREFULLY**

   - Cause: a free/undeclared identifier; NOT an implicit-parameter feature.
   - Fix: explicitly declare every used symbol in the parameter list (e.g., `(c : ℝ)`), or quantify it inside the statement (e.g., `∃ c : ℝ, ...`). Ensure types match usage: `c : ℝ` for `re/im` equality; `c : ℂ` if used as complex.
